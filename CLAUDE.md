# CLAUDE.md — Factorial API SDKs

## Project overview

Auto-generated SDKs for the Factorial public API in TypeScript and Python.
Each SDK wraps auto-generated OpenAPI client code with a generated
`FactorialClient` that exposes domain-namespaced methods, pagination helpers,
and clean auth handling.

Both SDKs use a multi-stage generation pipeline:
1. **Stage 1** — `openapi-ts` (TS) / `openapi-python-client` (Python) generates
   low-level typed functions from the OpenAPI spec into `generated/`.
2. **Stage 2** — a custom generator script produces the `FactorialClient` wrapper
   (`sdk.ts` / `client.py`) from the stage-1 output.
3. **Stage 3** — a webhook generator produces the typed webhook catalog
   (`webhooks.ts` / `webhooks.py`) from the spec's top-level `webhooks` object,
   and a shared generator (`scripts/generate_skill.py`) refreshes the
   `factorial-api-sdks` skill's `reference/` content.

The release script runs all stages automatically.

## ⚠️ Releasing & PRs — read before committing

Versioning, tagging, and publishing are **fully automated by release-please**.
**Never** hand-edit versions (`typescript/package.json`, `python/pyproject.toml`,
`.release-please-manifest.json`), create git tags, or run `npm publish` /
`uv publish` / the `release.ts` / `release.py` publish steps yourself. Full detail
in `RELEASING.md`. The rules that matter when opening a PR:

- **PRs are squash-merged, so the PR *title* is the commit release-please parses —
  it MUST be a [Conventional Commit](https://www.conventionalcommits.org/).**
  `feat:` → minor bump · `fix:` → patch · `feat!:` / `BREAKING CHANGE:` → major.
  `chore`/`docs`/`ci`/`refactor`/`test` do **not** trigger a release on their own.
- **Which package bumps is decided by file *path*, not the title scope.** Files
  under `typescript/` bump the npm package; files under `python/` bump the PyPI
  package; files elsewhere (`skills/`, `scripts/`, `CLAUDE.md`, root `README.md`,
  root config) bump **nothing** on their own.
- **A change touching both SDKs → use a bare `feat:` / `fix:` (no scope)** so both
  packages bump together. Only add a scope (`feat(typescript):`) for a change
  confined to one package.
- **There is no PR-level CI** — validate locally before opening:
  TS `npx tsc --noEmit` + `npm run build`; Python
  `uv run mypy factorial_api_client/` + `uv run ruff check factorial_api_client/`.
- Merging your PR does **not** publish. release-please then opens a per-package
  "Release PR"; merging *that* cuts the tag, GitHub Release, and registry publish.

## Auth

Two options — use one or both:

| Option | Header sent |
|--------|-------------|
| `apiKey` | `x-api-key: <value>` |
| `token` | `Authorization: Bearer <value>` |

Environment variables for smoke tests: `FACTORIAL_API_KEY`, `FACTORIAL_TOKEN`.

Note: the Factorial API key is JWT-formatted but sent as `x-api-key`, not bearer.

## Pagination

All list endpoints return `{ data: T[], meta: { end_cursor?, has_next_page, ... } }`.
Pagination params (`after_id`, `limit`) are not in the OpenAPI spec but work at runtime.

- `list()` — raw single page
- `paginate()` — async iterator (TypeScript) / sync or async generator (Python)
- `collectAll()` / `collect_all()` — fetches all pages into one array/list

## Webhooks

The OpenAPI spec's top-level `webhooks` object (127 events → 33 payload schemas)
drives a typed catalog in each SDK (`webhooks.ts` / `webhooks.py`), exported from
the package root:

- Clean per-event aliases, e.g. `AtsApplicationCreateWebhook` (= the payload type)
- `WebhookSubscriptionType` — union/`Literal` of every `subscription_type`
- `WebhookPayloadMap` (TS) / `WEBHOOK_PAYLOAD_TYPES` (Python) — `subscription_type` → payload type
- `WEBHOOK_CATALOG` — runtime list of every event

Delivery: Factorial POSTs the resource object **at the top level** (no `{type,data}`
envelope); the `challenge` is echoed in the `x-factorial-wh-challenge` header.

## factorial-api-sdks skill

A generic Claude Code skill teaching agents how to use the SDKs, installed
separately (NOT shipped in npm/PyPI):

```bash
npx skills add https://github.com/factorialco/factorial-api-sdks --skill factorial-api-sdks
```

`SKILL.md` is hand-written; `reference/` (webhook catalog + endpoint→SDK-call index,
both SDK-specific generated lookup tables) is regenerated by `scripts/generate_skill.py`
on every release. Human-oriented prose docs are intentionally NOT vendored — the
skill links to the live docs at apidoc.factorialhr.com instead.

## Regenerating the TypeScript sdk.ts

After running `openapi-ts` (stage 1), re-run the stage-2 generator:

```bash
npm run generate-sdk
# or: npx tsx scripts/generate-sdk.ts
```

This script (`scripts/generate-sdk.ts`):
- Parses all exported function names from `src/generated/sdk.gen.ts`
- Groups them by namespace and resource using the URL path naming convention
- Resolves multi-word namespaces (`ApiPublic`, `BookkeepersManagement`, `PayrollIntegrationsBase`, etc.)
- Classifies each function as `list`, `get`, `create`, `update`, `delete`, or a named custom action
- Emits `*Resource` classes (with `list`/`paginate`/`all`/CRUD/custom methods), `*Namespace` classes, and `FactorialClient`
- Writes the result to `src/sdk.ts`

The `release.ts` script calls this automatically after stage 1.

## Regenerating the TypeScript webhooks.ts

After stage 1, the stage-3 generator emits the typed webhook catalog:

```bash
npm run generate-webhooks
# or: npx tsx scripts/generate-webhooks.ts [specPathOrUrl]   # else OPENAPI_SPEC_URL, else latest
```

It parses `spec.webhooks`, maps each `subscription_type` to its payload type
(reusing the types already in `generated/types.gen.ts`), guards the known totals
(127 events / 33 schemas), and writes `src/webhooks.ts`. `release.ts` calls it
automatically; it also runs `scripts/generate_skill.py` to refresh the skill.

## Regenerating the Python client.py

After running `openapi-python-client generate`, re-run the generator script:

```bash
python /tmp/generate_python_sdk.py
```

This script:
- Parses `sync_detailed` signatures to split path params (positional) from query/body params (keyword)
- Deduplicates method names within a resource
- Renames `all()` → `collect_all()` when `all` is already used by an action endpoint
- Escapes Python reserved words (`in` → `in_`, etc.)

## Regenerating the Python webhooks.py

The stage-3 generator (in-repo, unlike `generate_python_sdk.py`) emits the typed
webhook catalog:

```bash
python scripts/generate_webhooks.py [specPathOrUrl]   # else OPENAPI_SPEC_URL, else latest
```

It mirrors the TS generator: clean aliases re-exporting the `generated/models/`
payload classes, a `WebhookSubscriptionType` `Literal`, a `WEBHOOK_PAYLOAD_TYPES`
dict, and `WEBHOOK_CATALOG`. `release.py` calls it (then `generate_skill.py`)
automatically. The file carries a `# ruff: noqa: E501` (long generated lines).

## Known gotchas

- **Spec `type: "unknown"` fields** — patched to `type: "string"` before generation (in `release.py`)
- **Enum null-safety** — spec marks many enum fields non-nullable but the API returns `null`.
  `release.py` post-patches generated `from_dict` call sites:
  `EnumClass(val)` → `EnumClass(val) if val is not None else None`
- **mypy on generated code** — 307 errors in generated files (245 unused `# type: ignore`,
  62 `Unset | None` mismatches). Excluded via `[tool.mypy] exclude` in `pyproject.toml`.
- **No `operationId` in spec** — generated names are verbose (e.g.
  `get_api_2026_04_01_resources_employees_employees`).
- **Semver bump logic** — defaults to minor; override with `--bump major|minor|patch`.
